Homework 2 - Parallel Matrix Convolution and Performance Benchmarking

Requirements analysis

The project implements a matrix convolution application that reads a source matrix F and a convolution mask C, computes the filtered result V, and compares the output with a sequential reference result. The source matrix is generated by the script scripts/generateMatrix.py and stored in files/MatrixF.txt. The convolution kernel is stored in files/ConvolutionM.txt.

The main functional requirements are:
- read the input matrix dimensions and values from text files;
- validate the kernel dimensions: it must be square and have an odd side length;
- compute the convolution result using a chosen execution strategy;
- support several executor types: sequential (s), horizontal (h), vertical (v), block (b), linear (l), and cyclic (c);
- run with a configurable number of threads p;
- compare the produced output with the sequential baseline before accepting the result;
- benchmark execution time over multiple runs and store the values in a CSV file;
- provide equivalent implementations in both C++ and Java.

The main constraints are:
- the kernel side length must be odd (for example 3x3, 5x5);
- the kernel must be square;
- the source matrix and output matrix sizes must be consistent with the convolution formula;
- result correctness is verified against the sequential reference rather than by heuristic comparison;
- for C++, the implementation supports both dynamic and static storage allocation;
- the documentation, source code, and generated results must be submitted together.

Design

The application is organized around a reusable matrix abstraction and a common executor interface.

The matrix model contains the following responsibilities:
- store matrix dimensions and values;
- load data from a text file;
- write the result to a text file;
- provide accessors and mutators;

In the C++ project, the abstraction is built in:
- model/Matrix.h and model/Matrix.cpp;
- model/DynamicMatrix.h and model/StaticMatrix.h.

The Java project contains the equivalent logic in:
- src/model/Matrix.java.

The convolution logic is separated from the scheduling logic. The base interface is:
- C++: executors/ConvolutionExecutor.h;
- Java: src/executors/ConvolutionExecutor.java.

Each concrete executor implements the same algorithmic kernel but uses a different partitioning strategy:
- SequentialExecutor: processes the entire matrix in one pass;
- HorizontalExecutor: partitions work by rows;
- VerticalExecutor: partitions work by columns;
- BlockExecutor: partitions the matrix into rectangular blocks;
- LinearExecutor: partitions by linearized index;
- CyclicExecutor: distributes indices cyclically among threads.

The actual work performed by each thread is encapsulated in task classes:
- SequentialTask, HorizontalTask, VerticalTask, BlockTask, LinearTask, CyclicTask.

The result matrix V stores the convolution of F and C at each (i, j) position.
The convolution element is computed as:

V[i][j] = sum over k, l of F[i + k][j + l] * C[k + offset][l + offset]

where offset = kernelSize / 2.

The overall program flow is:
1. read command-line parameters (thread count, executor type, allocation type for C++);
2. load F and C from the input files;
3. create the output matrix V;
4. create a sequential baseline if it does not already exist;
5. run the chosen executor;
6. write the output to files/output.txt;
7. compare output.txt with files/sequential.txt;
8. print the elapsed time in milliseconds;
9. append execution results to the CSV report.

Implementation details

The core convolution operation is performed by Matrix::convolveAt(...) in the C++ implementation and by the corresponding logic in the Java model implementation. This function iterates over the convolution kernel and accumulates the weighted sum of the overlapping source pixels.

The program ensures correctness by generating a sequential reference output before or during the test. When a non-sequential executor is used, the system verifies that the output matrix matches the sequential reference. If the file content differs, the application throws an error and stops.

The C++ implementation uses a static or dynamic output matrix depending on the allocation mode chosen by the caller. When the mode is static, data is allocated in a fixed-size structure; when the mode is dynamic, it is stored in a resizable matrix object. This design allows the project to compare behavior under different memory allocation strategies.

The Java implementation follows the same logic but uses a single runtime-managed matrix representation. The Java project is simpler from an allocation point of view, but it still supports all required executor types and validates correctness against the sequential baseline.

The batch runner is implemented in scripts/script.sh and scripts/run_all.sh:
- script.sh builds the C++ project (if required), compiles Java classes, executes a single configuration, validates the result, and records timing information;
- run_all.sh iterates across all required combinations of language, executor type, thread count, and matrix sizes and writes the aggregate results into hw2/all_results.csv.

The benchmark data is stored in CSV format with the following columns:

timestamp, language, type, allocation, n, m, k, threads, run, time_ms

The average for each configuration is appended at the end of the file as a final row with run value equal to average.
The consolidated comparison is in TABLE.csv. It contains one average-time row
for each configuration, plus a speedup column. Unlike the raw run-level CSV,
TABLE.csv is arranged in six-row groups, one for each executor type in this
order: s, h, v, l, c, b.

Test cases

The correctness and performance verification uses the scripts under the hw2/scripts folder.

1. Generate matrix inputs

Command:
python3 scripts/generateMatrix.py 10 10 3
python3 scripts/generateMatrix.py 1000 1000 3
python3 scripts/generateMatrix.py 10 10000 5
python3 scripts/generateMatrix.py 10000 10 5
python3 scripts/generateMatrix.py 10000 10000 5

The generator writes:
- files/MatrixF.txt
- files/ConvolutionM.txt
- existing output files are removed before the next run to ensure a fresh sequential reference.

2. Single-run validation

Examples:
./scripts/script.sh cpp s 4 10 dynamic
./scripts/script.sh cpp h 8 10 static
./scripts/script.sh java c 4

The script validates:
- the required number of arguments;
- valid executor type values: s, h, v, b, l, c;
- valid positive thread count;
- valid odd-square convolution mask;
- correct output file generation;
- equality between output.txt and sequential.txt.

3. Full benchmark matrix

The project covers the required workload matrix sizes and thread counts:
- 10x10 with 3x3 kernel, threads: 2, 4, 8, 16
- 1000x1000 with 3x3 kernel, threads: 2, 4, 8, 16
- 10x10000 with 5x5 kernel, threads: 2, 4, 8, 16
- 10000x10 with 5x5 kernel, threads: 2, 4, 8, 16
- 10000x10000 with 5x5 kernel, threads: 2, 4, 8, 16

The full benchmark command is:
./scripts/run_all.sh

A dry-run is also supported:
./scripts/run_all.sh --dry-run

To resume at a configuration ID (inclusive), preserving previous results in
hw2/all_results.csv, use:
./scripts/run_all.sh --start-id 257

The configuration IDs are 1-based and range from 1 to 306. The run count can
also be specified when resuming, for example:
./scripts/run_all.sh 5 --start-id 257

The benchmark checks both Java and C++ implementations, and C++ runs with both dynamic and static allocation modes.

Results analysis

The runner records each execution and calculates an average time for every
configuration. The raw run-level results are written to all_results.csv. The
consolidated TABLE.csv is intended for comparing those average times and their
speedups across executor types, languages, C++ allocation modes, matrix sizes,
and thread counts.

Each group in TABLE.csv contains exactly six rows for the same language,
allocation mode, matrix dimensions, kernel size, and thread count. The first
row is the sequential execution (s); the remaining rows are horizontal (h),
vertical (v), linear (l), cyclic (c), and block (b). The speedup column is
calculated using the sequential time from that same group:

speedup = time_ms(s) / time_ms(executor)

The sequential row therefore has a speedup of 1.0. A value greater than 1.0
means that executor was faster than the sequential version for that
configuration; a value below 1.0 means it was slower. The baseline must not
be shared across groups: each language, allocation mode, matrix/kernel size,
or thread count has its own sequential reference.

For example, the first group in TABLE.csv is C++, dynamic allocation, a 10x10
matrix with a 3x3 kernel, and 4 threads. The sequential time is 0.017249 ms.
The horizontal time is 0.248478 ms, so its speedup is
0.017249 / 0.248478 = 0.069418620562. The sequential row has speedup
1.000000000000, and every other row in the group uses 0.017249 ms as its
numerator. This indicates that parallel thread overhead dominates for this
small workload.

TABLE.csv contains 306 data rows, or 51 complete executor groups. It includes
the benchmarked Java and C++ configurations; C++ configurations are listed
separately for dynamic and static allocation. The results show that relative
performance depends on workload shape, kernel size, thread count, language,
and allocation mode. There is no single executor that is fastest in every
case, so the per-group speedup is the appropriate way to compare each
parallel strategy with its matching sequential baseline.

The results also confirm that correctness checks are integrated into the benchmarking flow. Every execution compares the output file with the sequential reference before recording the timing data. If the matrix is incorrect, the benchmark is stopped and the failure is reported immediately.

Summary

This homework demonstrates three major ideas:
- parallel partitioning strategies can be used to distribute convolution computation;
- correctness must be validated against a sequential reference for every test case;
- performance must be measured systematically and reported through repeatable benchmarks.
