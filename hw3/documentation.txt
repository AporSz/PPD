Homework 3 - In-place 3x3 Matrix Convolution

Requirements analysis

The program applies a 3x3 convolution filter to an input matrix F. Its
postcondition is that the input matrix itself contains the filtered result.
The implementation must not allocate a second result matrix or a temporary
matrix. Temporary vectors are allowed if their space usage is O(n) for a
matrix with n rows and n columns.

The required implementations are Java and C++. The only
execution strategies are sequential execution and line-based distribution:
horizontal (row-based) and vertical (column-based). C++ uses dynamic matrix
allocation only.

The input is generated before execution and saved as files/date.txt. The
convolution kernel is saved as files/ConvolutionM.txt and must be 3x3. The
filtered matrix is written to files/output.txt. The sequential result is
written to files/sequential.txt and is used as the correctness reference.

Required performance cases:
- N=M=10: sequential and line-based execution with p=2;
- N=M=1000: sequential and line-based execution with p=2, 4, 8, and 16;
- N=M=10000: sequential and line-based execution with p=2, 4, 8, and 16.

Every configuration is executed 10 times using the same generated input.
The arithmetic mean of the 10 timed executions is the reported time. Each
execution must be checked against the sequential output. The analysis compares
line-based and sequential execution for each case, compares Java with C++, and
evaluates additional space usage.

Design

The source matrix is the only result-bearing matrix. The filter matrix C
contains the 3x3 kernel and is read-only during convolution.

The matrix classes provide file loading, indexed access, row copying, row
writing, and file output:
- C++: model/Matrix and model/DynamicMatrix;
- Java: model/Matrix.

The execution interface has three implementations:
- SequentialExecutor processes rows in order;
- HorizontalExecutor divides the rows into contiguous ranges and runs one
  task per worker;
- VerticalExecutor divides the columns into contiguous ranges and runs one
  task per worker.

Each output row is computed from the original values in the rows above, at,
and below it. At image boundaries, the nearest edge value is replicated.
Because the convolution is in place, a row is calculated into a temporary
vector before replacing that row. The sequential algorithm maintains a
three-row sliding window. The horizontal algorithm keeps copies of partition
boundary rows, and the vertical algorithm keeps copies of partition boundary
columns, so workers do not read neighboring data after it has been
overwritten.

Implementation details

The generator scripts/generateMatrix.py creates date.txt and a random 3x3
ConvolutionM.txt. It removes any previous sequential and output files so a
new input cannot accidentally use an old reference.

Both programs load date.txt directly into a dynamically allocated matrix
(C++ uses DynamicMatrix; Java uses its runtime-managed int[][] matrix). They
do not allocate an output matrix. The 3x3 kernel is loaded separately.

For sequential execution, the program times the in-place operation, writes the
result to output.txt, and saves the same result as sequential.txt. For a
line-based run, the runner first creates a sequential reference if one is not
already available for the generated input. The parallel process then loads
the original date.txt into its own single matrix, applies the filter in place,
writes output.txt, and compares the result with sequential.txt.

The timer covers the convolution execution only. File loading, reference
creation, output writing, and correctness comparison are outside the measured
interval.

The scripts are:
- scripts/generateMatrix.py: creates the input matrix and 3x3 kernel;
- scripts/script.sh: builds or compiles one implementation, executes it
  exactly 10 times, checks every result, and records each time and the mean;
- scripts/run_all.sh: runs the required language, executor, thread-count, and
  matrix-size combinations and writes the means to all_results.csv.

The CSV columns are:

timestamp,language,type,allocation,n,m,k,threads,run,time_ms

For C++, allocation is always dynamic. For Java, allocation is
not-applicable. script.sh writes ten run rows numbered 1 through 10 and an
additional average row to its selected CSV. run_all.sh writes one average row
per configuration to all_results.csv.

Testing procedure

From the hw3 directory, run the complete required benchmark suite:

./scripts/run_all.sh

The suite generates these input sizes, all with a 3x3 kernel:
- 10x10;
- 1000x1000;
- 10000x10000.

For the 10x10 case, it runs one sequential configuration and horizontal and
vertical line-based configurations with p=2 for each language. For each
larger case, it runs one sequential configuration and horizontal and vertical
line-based configurations with p=2, 4, 8, and 16 for each language. This
results in 42 configurations, each repeated ten times.

Use a dry run to list the configuration count without executing benchmarks:

./scripts/run_all.sh --dry-run

To resume at a 1-based configuration ID while keeping the existing CSV:

./scripts/run_all.sh --start-id 13

The runner checks each timed output against the sequential reference before
recording its time. If any run fails, it reports the failure and stops instead
of recording a successful average for that configuration.

Results analysis

Use all_results.csv to compare the average sequential, horizontal, and
vertical times within each language, input size, and thread count. Compare the
corresponding Java and C++ rows for each configuration to assess language
performance. A speedup can be calculated as:

speedup = sequential average time / (horizontal or vertical average time)

A speedup greater than 1 means the line-based executor was faster; a value
below 1 means it was slower. The 10x10 case is especially useful for seeing
the effect of thread creation overhead, while the larger cases show whether
the work benefits from distributing rows or columns. Timing results depend
on the machine and runtime, so use the generated CSV rather than assuming a
fixed winner.

Space complexity

The matrix itself requires O(NM) storage and is the only source/result matrix.
The 3x3 kernel requires constant O(1) storage. Sequential execution keeps a
constant number of row vectors, so its additional space is O(M). Horizontal
execution keeps a bounded number of row vectors per worker (partition
boundaries and one row being computed), giving O(pM) additional space for p
workers. Vertical execution uses column vectors and requires O(pN) additional
space. The required benchmark caps p at 16, so each approach uses space
linear in its line length; neither allocates a temporary matrix.
